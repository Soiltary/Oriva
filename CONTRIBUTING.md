# Contributing

Preserve the existing Win32 and shared web architecture. Describe the trigger and expected behavior, use synthetic fixtures, fix the cause and add meaningful regression coverage. Keep patches focused. Run the documented tests/typecheck/build affected by the change. Never commit credentials, Site identity, live database/file exports, user data, runtime directories or binaries. Update English and Arabic docs together. Do not publish or activate update manifests as part of an ordinary code change. Assess storage changes by their actual operations: preserve applied SQL/snapshots/journal entries, rehearse additive extensions with synthetic data and verify the hosted schema/API after publication. Destructive changes, resets and resource deletion need explicit target-specific approval and verified recoverability. A tested schema-only first-launch append can use the supported publishing workflow under the owner's explicit risk acceptance; unavailable provider-wide backup is not proof that an additive change deletes data. Disclose unverified provider disaster recovery, possible migration-before-Worker failure and schema-compatible forward repair/containment. Never assume code rollback restores data. Source availability does not mean the candidate is Stable.
