## Maximum single-file restore rehearsal — 2026-10-28

`node tests/restore-capacity-runtime.mjs` runs against disposable actual local D1/R2 with outbound requests denied. A file at the true API boundary, 25 MiB (26,214,400 bytes), was uploaded, streamed in25 blob chunks, staged, resumed after Worker reconfiguration during upload and commit, restored and downloaded with identical SHA-256 `a1df3c56c879f59b19bb679784bb1227add4042f41afddcf6979c14f4886b7a6`. Duplicate retry and completed commit did not create duplicate items. Cross-account access returned404. Rollback retained the imported item's recoverable trash tombstone while preserving the source account and original bytes. There were28 records and28 commit calls.

The initial fixture used25,000,000 bytes and incorrectly expected rollback to remove modern synchronization tombstones. Those test assumptions were corrected to the actual 25×1024×1024 limit and documented recoverable-trash contract; no application code was changed to make the test pass. The final test passes.

This closes the maximum **single-file** interrupted-restore rehearsal only. It does not establish whole-library storage capacity, long-running endurance or a retention policy. Temporary restore records and R2 chunks currently have no verified bounded retention/aggregate capacity policy. The10,000-item count cap alone could permit about244 GiB of final file data at the maximum per-file size, plus staging/backup overhead; this is an arithmetic upper bound, not a measured supported workload. Before Stable, define provider-compatible byte/session quotas, durable admission accounting, bounded retry-safe cleanup of temporary prefixes only, preservation of active resumes and completed/rolled-back history, then test concurrency, expiration and crash recovery under the actual resource plan. No cleanup or expiry was activated in production.
