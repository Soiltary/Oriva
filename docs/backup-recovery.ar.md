# النسخ الاحتياطي والاستعادة لموارد Oriva المُدارة عبر Sites

## القرار الحالي ونطاق التحقق

**ترحيلات الإنتاج ونشر API وإصدار Windows المستقر معلّقة.** قاعدة D1 وتخزين R2 مُداران عبر ChatGPT Sites ، ولا يملك صاحب المشروع وصولًا مباشرًا إلى Cloudflare أو نسخة مزوّد كاملة ثبتت إمكانية استعادتها. لم نطلب مفاتيح Cloudflare ، ولم ننزّل سجلات مستخدمي الإنتاج أو ملفاتهم.

أكد اتصال Sites المشروع القائم ونسخ المصدر وربطي التخزين `DB` و`BUCKET`. يعرض ملخص D1 الحالي جداول `attempts` و`items` و`sessions` و`users`. تؤكد نسخة المصدر المحفوظة 17 الترحيلات 0000–0002. هذه معلومات عن البنية، وليست نسخة بيانات. حفظ نسخة من الموقع أو تنزيل مصدره لا يثبت حفظ سجلات الزوار أو المرفقات.

## ما تتيحه الأدوات وما لم يثبت

| القدرة | النتيجة الفعلية |
|---|---|
| تاريخ المصدر والنشر | يعرض Sites النسخ المحفوظة ومرجع Git وأرشيف المصدر. نطاقه الشفرة وآثار النشر. |
| فحص D1 | توجد نظرة عامة وقراءة محدودة بصفحات؛ لا توجد في أدوات الجلسة عملية تصدير كامل متسق أو استعادة كاملة. نسخ صفوف متفرقة لا يحقق شرط التعافي. |
| نسخة D1 كاملة أو نقطة استعادة | لا تعرض أدوات الاتصال الحالية هذه العملية، ولم تثبت الوثائق عقدًا متاحًا لهذا المشروع لنسخ العميل واستعادته. قد توجد نسخ داخلية لدى المزوّد؛ مدة الاحتفاظ وإمكانية الاسترجاع غير متحققتين. |
| R2 كامل | لا توجد عملية معلنة لجرد الدلو بجميع صفحاته وتنزيل كل كائناته أو إنشاء لقطة أو استعادتها. اعتماد مستودع المصدر لا يمنح وصولًا إلى بيانات التخزين. |
| قدرات Cloudflare | توثق Cloudflare تصدير SQL و Time Travel: حتى 30 يومًا للخطة المدفوعة و 7 للمجانية، لكن خطة موارد Sites الفعلية ونقاطها غير معروفتين. الاستعادة المباشرة تستبدل قاعدة الهدف، فلا تصلح كتجربة على الإنتاج. |
| واجهة R2 المتوافقة مع S 3 | تدعم الجرد المقسّم وقراءة الكائنات وبياناتها الوصفية؛ جدول التوافق لا يدعم إصدار الدلو التاريخي. لا يصح افتراض وجود لقطة أو إصدارات سابقة للكائنات. |

تفرّق وثائق OpenAI بين نسخة الموقع وبيانات الزوار: [إنشاء موقع](https://learn.chatgpt.com/docs/sites/creating-a-site)، [إدارة موقع](https://learn.chatgpt.com/docs/sites/managing-a-site)، [البيانات والاتصالات](https://learn.chatgpt.com/docs/sites/data-and-connections). المراجع التقنية: [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)، [استيراد وتصدير SQL](https://developers.cloudflare.com/d1/best-practices/import-export-data/)، [واجهة التصدير](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/)، [توافق R2](https://developers.cloudflare.com/r2/api/s3/api/)، [صلاحيات R2](https://developers.cloudflare.com/r2/api/tokens/)، [قفل الدلاء](https://developers.cloudflare.com/r2/buckets/bucket-locks/).

قد يوقف تصدير D1 عبر واجهة المزوّد إتاحة القاعدة مؤقتًا؛ لم نبدأ تصديرًا حيًا ولم نفترض نافذة صيانة. قفل R2 يمنع الحذف أو الاستبدال لكنه ليس نسخة تاريخية، وتفعيله ارتجالًا على الإنتاج قد يعطّل تنظيف الملفات الطبيعي.

## أقل تدخل مطلوب من مزوّد Sites

المطلوب دعم تصدير واستعادة **مقيّد بمشروع Sites**، وليس حساب Cloudflare إداريًا أو مفتاحًا عامًا أو صلاحية كتابة SQL في الإنتاج. يمكن للمزوّد تنفيذ الآتي بنفسه بدل منح اعتماد واسع:

1. تصدير كامل ومتسق لبنية D1 وبياناتها عند نقطة موثقة، شاملًا جميع الجداول والعلاقات والفهارس وسجل الترحيلات والبيانات اللازمة للاستعادة. جداول المصادقة حساسة وتبقى خاصة.
2. جرد R2 بجميع الصفحات وتصدير كل المفاتيح والبايتات والأحجام وبيانات HTTP والبيانات المخصصة، مع الأزمنة و ETag إن توفرت، بما يشمل مراجع الملفات والصور والإصدارات والعناصر المحذوفة القابلة للاسترجاع.
3. إثبات اتساق SQL مع مجموعة الكائنات. الكود الحي قد يحذف صورًا أو ملفات مستبدلة؛ الجرد المتحرك لا يضمن استرجاع كائن اختفى أثناء الالتقاط. يلزم اقتران موثق أو إجراء اتساق معتمد لا يحذف سجلات المستخدمين ولا يغيرها.
4. قناة نقل خاصة ووجهة نسخ دائمة مستقلة وسياسة احتفاظ وصلاحيات واضحة؛ لا GitHub ولا روابط عامة أو سجلات محادثة أو رفع عادي إلى الموقع. تُشفّر الآثار ويُحفظ مفتاح التعافي في خزنة منفصلة يسيطر عليها المالك.
5. استعادة نسخة فقط إلى D1 و R2 جديدين ومعزولين بربوط منفصلة ومنع الاتصالات الخارجية. لا نطلب حذفًا أو تصفيرًا أو استبدالًا للإنتاج أو تبديل روابطه أو استعادة مكانية فوقه.
6. تقرير استعادة فعلي يحدد معرفات النسخ وزمن الالتقاط ومكان التخزين ومدة الصلاحية والاحتفاظ وحدود نقطة التعافي وكيفية التعامل مع الكتابات اللاحقة. إرجاع الشفرة وحده لا يعكس الترحيلات أو يسترجع ملفات R2.

إذا لم توجد آلية مدعومة، يظل الشرط غير محقق. لا نضيف نقطة تصدير عامة ولا ننتحل حسابات المستخدمين ولا ننشر مُصدّرًا يحتاج تعديل بنية الإنتاج لمجرد الحصول على نسخة.

## قبول الاكتمال والسلامة

يظل البيان التفصيلي خاصًا: بصمة SQL وبنية القاعدة والترحيلات، وعدد الصفوف والبصمة القياسية لكل جدول، ومفاتيح R2 وأحجامها و SHA-256 وبياناتها الوصفية وإجمالي البايتات وحد الالتقاط. ETag وحده ليس بديلًا مضمونًا لبصمة كامل الكائن. تُراجع مراجع المرفقات والصور والإصدارات كلها، وتُحفظ الكائنات الزائدة بدل حذفها لإجبار الأعداد على التطابق.

تُشفّر النسخة بتوثيق سلامتها قبل النقل، ويُفصل المفتاح عنها. تكون تجربة الاستعادة من النسخة المخزنة المعاد فتحها، لا من الذاكرة أو المصدر الحي. يجب رفض المفتاح الخاطئ والنص المشفر المعدّل و SQL المعدّل والكائن الناقص أو المتغير قبل الاستعادة.

في البيئة المعزولة تُفحص سلامة SQLite والأعمدة والفهارس والأعداد والبصمات قبل أن يغير تسجيل الدخول جداول الجلسات والمحاولات. تُراجع الملفات وبياناتها الوصفية والمصادقة وملكية الحسابات وعزلها والإصدارات والتنزيلات. تُجرّب الترحيلات على نسخة إضافية مع إبقاء نسخة التعافي الأصلية. لا توجّه الخدمة المستعادة إلى تخزين الإنتاج.

## تجربة محلية أُنجزت

الأمر أداة التحقق الخاصة بالاستعادة المعزولة ينشئ بيانات اصطناعية محلية في workerd و D1 و R2، ثم يستخدم أوامر Wrangler الرسمية المحلية لتصدير SQL واستيراده إلى مساحة جديدة. لا يقبل اعتماد إنتاج أو إعداداته ولا يستعيد فوق المصدر.

نجحت ثمانية اختبارات شملت 12 جدولًا وثلاثة كائنات R2، منها ملف ثنائي حجمه 1.1 ميغابايت وصورة وبيانات HTTP ومعلومات مخصصة. شملت التحقق من كل الصفوف والبايتات، وتشفير AES-256-GCM وإعادة فتح الأثر المخزن بمفتاح اصطناعي منفصل، ورفض العبث والمفتاح الخاطئ والكائن الناقص، وفحص SQLite وتسجيل الدخول وعزل الحسابات وتنزيل الملف المستعاد.

SQL والمفتاح والنسخة المشفرة الاصطناعية تبقى خارج المصدر العام. هذه تجربة صغيرة وليست مُصدّرًا متدفقًا بحجم الإنتاج أو إثباتًا لصلاحيات مخزن دائم مستقل أو لزمن الاستعادة أو لوجود نسخة Sites فعلية. نجاحها لا يمرر بوابة تعافي الإنتاج.

## استراتيجية الإصدار الآمنة

- الحفاظ على الموقع وبياناته الحالية وتأجيل الترحيلات 0003–0007 وواجهة API الجديدة.
- نشر المصدر المراجع بترخيص MIT والتوثيق الثنائي اللغة بصورة مستقلة عن الإصدار المستقر القابل للتنزيل.
- تجهيز Windows 1.0.0 كمرشح خاص مع بصماته، وفصل رقم المنتج العام عن ترتيب التحديث التقني 2.0.0؛ لا تفعيل للبيانات الوصفية للتحديث ولا وسم Stable.
- إبقاء التنزيلات والتحديثات الحية حتى التحقق من API المتوافق وروابط التنزيل المباشرة من الأصل نفسه. العميل الجديد يحتاج مسارات غير موجودة في API المنشور حاليًا.
- الحصول على نسخة D1 و R2 مقترنة واستعادة معزولة موثقة، ثم حل توافق العملاء القدامى وبقية بوابات السلامة والقبول قبل نشر المكونات وتفعيل التحديث بالترتيب المتحقق منه.

الخلاصة الدقيقة: لم يثبت وجود مسار كامل ومتاح لهذا الحساب والمشروع لتصدير D1 و R2 واستعادتهما عبر واجهة إدارة Sites المتاحة. هذا لا يدّعي أن Sites لا يحتفظ بأي نسخ داخلية.
