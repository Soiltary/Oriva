# First public release strategy

[العربية](first-release-strategy.ar.md)

The owner confirmed on2026-10-28 that Oriva has no external users, no supported public1.5.3 installed base and no valuable content in its development accounts. The first official product release is1.0.0 in the existing Oriva Site/repository under MIT. Preserve existing code, history, installed development software and current resources. Existing-resource deletion/reset still requires exact target/impact confirmation.

Unpublished-client write compatibility and migration of nonexistent customers are no longer release gates. Keep revision checks and reject unsafe stale writes. Keep product1.0.0 separate from monotonic updater ordering2.0.0 to avoid distributing a downgrade to the owner's development installation; do not activate its automatic update without verification.

The owner selected an enforced account allowance of512MiB for files/images and32MiB for content, revision history and charged metadata. The10,000-item limit remains. Trash/history count. The content allowance includes escaped UTF-8 fields plus2KiB of bookkeeping per record; it is not a promise of32MiB of raw editable text alone. Staging permits two active restores,1GiB of chunks and64MiB of record payloads per owner, with seven-day expiry and explicitly confirmed, bounded cleanup of temporary prefixes. These larger staging allowances must restore a complete valid account, not merely reject large backups.

Fresh local actual D1/R2 rehearsal passed536,870,912 file bytes plus33,546,690 charged metadata bytes:21 files,33 articles and history,569 staging records/commit calls, two Worker runtime reconfigurations, all target file hashes and exact source/target quota equality. Temporary data cleanup completed in12 bounded calls while source bytes and final saved data remained. This is local functional/capacity evidence, not a provider disaster-recovery guarantee. The initial run caught unwanted non-file filename fallback during restore; the corrected run passed. All28 synthetic suites pass at the latest local checkpoint.

`scripts/first-release-schema.mjs` derives15 fresh tables and accounting triggers from the existing model without development seeds or0004's collection backfill. It has no deploy/apply client and must target a verified-empty database. It passed fresh SQLite and actual local D1/R2 authentication/restore tests. Historical migrations0000–0007 remain unchanged. New local migrations0008/0009 are additive/schema-only. The existing hosting build still packages its historical chain; the new generator is not silently substituted for a deployed database's migration history.

Current Sites metadata still reports the existing public owner project atversion17 with four base tables. Existing tools do not expose a complete D1/R2 capture, isolated disaster restore, actual internal migration ledger, or clean-resource replacement operation. A library export is not an all-account/provider backup. Resolve the exact supported pending-migration repair or fresh-resource path within the same Site before deployment. No current data cleanup, cloud migration or deployment has occurred.

Settled failed-upload reclamation, full-quota trash/undelete and confirmed permanent purge are now implemented and regression-tested. Process-death recovery of pending/purging reservations remains a Stable gate. The schema-only hosted-baseline bridge is prepared offline; it has not replaced hosted migration history. See [current storage/recovery status](storage-recovery-status.md) for verified coverage and remaining gates.
